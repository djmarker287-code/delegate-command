# Delegate

The model selected for the current chat is the planner, router, coordinator, and final decision maker. Workers do the substantive assigned work and return evidence. The coordinator verifies results and keeps work moving through agents until the user's task is complete. Routing settings persist across chats in the user-level Codex home as `delegate.json` (`~/.codex/delegate.json` by default).

Run `python <installed delegate skill directory>/scripts/delegate.py <command>` to manage settings. Resolve the script path from this `SKILL.md` location. `status` reports `mode`, `models`, `max_agents`, and `priority`; `models` lists catalog candidates. `priority <balanced|speed|cost|quality>` saves the routing preference. Report the coordinator's model only when reliable session context provides it. Never infer it from user-level config because the chat can override that config.

## Invocation

- `delegate auto <number>` or `delegate select auto <number>`: Save automatic model selection with a maximum of that many agents per task. The number must be 1–6. Omit the number to keep the current limit.
- `delegate count <number>`: Change the per-task agent limit to a number from 1–6 without changing the mode.
- `delegate select <model> [<model> ...]`: Save a manual worker model pool. The chat model stays the coordinator; the planner chooses a subset of that pool per task.
- `delegate manual`: Switch back to the saved manual pool without re-entering its model IDs.
- `delegate add <model> [<model> ...]` or `delegate remove <model> [<model> ...]`: Edit the manual pool.
- `delegate models`, `delegate status`, `delegate reset`: List candidates, show the setup, or reset to auto mode with a limit of three.
- `delegate priority <balanced|speed|cost|quality>`: Set the routing preference for new tasks.
- `delegate start [--budget-tokens N] [--budget-usd N] <task>`: Start a tracked task with optional per-task limits. `delegate <task>` starts a tracked task without a budget.
- `delegate runs`, `delegate progress [run-id]`, `delegate calls [run-id]`: Inspect saved run IDs, progress, or call history. Use the current chat's run ID when omitted; if unknown, list runs.
- `delegate pause [run-id]`, `delegate resume [run-id]`, `delegate stop [run-id]`: Pause new dispatch, resume a paused run, or stop it. On stop, interrupt active agents when the tool permits and report any work that could not be interrupted. A checkpoint remains for review; stop does not erase it.
- `delegate diagnostics`: Check local settings and saved runs; check agent-tool, model, resume, and usage availability in the live session. The helper cannot inspect live tools by itself.
- `delegate` without a task: Activate delegation for this chat and show the setup.
- `delegate off`: Stop delegating in this chat while retaining the saved army for future use.
- `delegate <task>`: Activate delegation and carry out the task. Auto mode picks worker models from the available catalog. Manual mode picks only from the saved pool; if that pool is empty, ask the user to select a model or switch to auto.
- `delegate goal <objective>`: If no goal is active, use the available goal command or tool to create the goal. Add this concise condition to its objective: "On every continuation, use the delegate skill; re-read the user-level Codex delegate.json; keep the chat model as planner and router; keep assigning distinct remaining work to agents and reuse them within the saved maximum of six distinct agents until the objective is complete; log calls and elapsed times." If a goal is already active, do not replace its objective; treat this command as steering that goal unless the user explicitly asks to replace it. The goal's completion audit, budget, and lifecycle still govern the work.

After activation, use delegation on later tasks in this chat until the user turns it off. Read `status` at the start of each task, including goal continuation turns, so changes from other chats take effect. A normal `/goal` started after delegation is active should continue with this routing behavior; `delegate goal` also writes the routing condition into the goal objective so it survives compaction. In Plan mode, delegate only planning or research and preserve the no-implementation boundary. In review workflows, delegate independent inspections and let the coordinator synthesize the findings. Other workflows keep their own requirements.

## Tracked task flow

For a substantive delegated task, use `python <installed delegate skill directory>/scripts/run.py start "<objective>"` and retain its returned run ID. Optional `--budget-tokens` and `--budget-usd` set limits for that run. `run.py list`, `status <id>`, and `progress <id>` recover the checkpoint across chats and compaction. The checkpoint stores a concise progress summary and agent history; it does not save or schedule a full task backlog. The coordinator still decides the next ready work from the objective and evidence. On continuation, read the checkpoint and inspect the actual workspace before dispatching.

Before dispatch, estimate whether the assignment's expected value outweighs tool latency and coordination cost. Apply the saved routing priority, task complexity, and observed evidence. `run.py recommend <id> <routine|general|complex> <candidate-model...>` summarizes prior outcomes, elapsed times, and cost when recorded; its small samples are advisory. Check live model availability. In auto mode, try another suitable available model if a spawn fails. In manual mode, try another saved model only; if none works, show the failure and available choices. Record the chosen model actually used. Never silently switch outside the manual pool or claim measured savings without usage data.

Before each spawn or follow-up, check `run.py progress <id>` for `idle_agents`. Reuse a suitable idle agent with `followup_task` before creating a new one. If all existing agents are busy, wait for one when that is faster or cheaper than spawning. Spawn an additional agent only for a concrete reason such as useful independent parallel work or a required model capability; pass that reason as `--new-agent-reason "<reason>"`. An existing agent keeps its original model, so do not claim that a follow-up changes it. Call `run.py assign <id> <agent> <model> "<purpose>" --kind <routine|general|complex> --expected "<output>" --accept "<completion check>"` and add `--owns <path>` for files the agent will edit. The helper rejects an unjustified new agent, a seventh distinct agent, duplicate purpose, overlapping active file ownership, and concurrent work on the same agent. Record the actual tool call with `run.py call <id> <tool> <target> "<purpose>" "<outcome>"`. If a spawn fails, use `run.py spawn-failed <id> <agent> "<reason>"` so the failed attempt does not consume a distinct-agent slot; then choose an allowed fallback. On observed completion, use `run.py finish <id> <agent> <success|failed|blocked> "<result>"`; send failed checks back as a distinct repair assignment with `--retry-of <assignment-id>`. Keep assigning the next ready work until the objective is complete.

Update `run.py checkpoint <id> "<concise progress and next action>"` after meaningful changes, particularly before ending a turn. Use `run.py pause|resume|stop <id>` for lifecycle controls. Record provider-reported usage with `run.py usage <id> <agent> <tokens|unknown> <usd|unknown> [--score 1-5]`, or rate a completed assignment with `run.py rate <id> <assignment-id> <1-5>`. Use `unknown` for a metric the platform does not supply; never invent token or cost numbers. Under a budget, provide pre-dispatch estimates with `--estimate-tokens` and/or `--estimate-usd`, and record actual usage after each completion before another dispatch. If the metric required by the budget is unavailable, pause budgeted dispatch and explain that the budget cannot be reliably enforced. Estimates and reported usage are checks, not a provider-side hard spending cap; an individual call can exceed its estimate. The helper records events but cannot spawn, resume, interrupt, or meter agents itself; use the session's actual tools for those actions.

For an activated delegated task, use workers for substantive research, implementation, and routine fixes. The coordinator plans, routes, tracks dependencies, checks results, and gives the final answer; it does not take over the unfinished work when the first assignments return. Direct coordinator implementation happens only when the user explicitly asks it to step in or no usable worker is available; explain that exception. The saved `max_agents` is a ceiling on the **total distinct agents spawned for one task**, including descendants and sequential spawns, never a target; six is the hard maximum. Prefer follow-ups to existing agents over fresh spawns to avoid setup time and usage. Reassigning an agent does not create another distinct agent. If the platform cannot resume an agent and the distinct-agent limit is reached, do not evade the limit or silently switch the remaining work to the coordinator; report the limitation and ask for direction. Also obey the platform's concurrency limit. In auto mode, pick the best available model for each agent's initial assignment from the current catalog. In manual mode, choose a subset of the saved pool. Prefer a faster, lower-cost model for bounded routine work and a stronger model when task complexity or error cost warrants it; consult current model capability and price information when needed, and do not promise savings without usage evidence.

Maintain a task backlog with dependencies and completion criteria. Dispatch a useful first batch of distinct assignments. Whenever an agent finishes, inspect its evidence, record the result, update the backlog, and give the next ready assignment to an idle agent. Keep doing this through all remaining batches, including fixes and verification work, until the task's completion criteria are met or a real blocker prevents progress. The agent limit caps simultaneous and distinct agents, **not the number of assignments or follow-up calls**. Do not declare the task done because the first batch finished. Keep the coordinator's own work to planning, routing, light integration, verification, and the final report; delegate substantial fixes unless the user directs otherwise.

Make an assignment ledger only for agents actually used, with a unique task, expected output, and file ownership where relevant. Do not assign the same investigation, implementation, or review to multiple workers or invent work to fill the limit. Pass the chosen model explicitly to each spawn. If model override requires a context-free fork, provide full task context. Keep routing at the coordinator; workers should not spawn descendants unless the coordinator explicitly budgets them within the six-agent total. If a model cannot be spawned, report the failure and do not silently substitute another. Workers may edit separate files; the coordinator resolves shared changes and verifies the final result. Honor user instructions, tool permissions, and workflow boundaries.

## Call and time report

For each subagent call, record its tool name (`spawn_agent`, `followup_task`, `send_message`, `wait_agent`, or `interrupt_agent`), target agent, chosen model when applicable, unique assignment or message purpose, and outcome. Capture the current clock time immediately before a worker is spawned or given a follow-up task and when its completion is observed. Calculate elapsed wall time for each work interval. If the platform provides actual active runtime, report that separately; otherwise label the measurement **dispatch-to-completion elapsed time**, which can include queueing and waiting. Do not invent missing times.

At the end of every delegated task, include a concise table with each used worker's model, assignments across batches, results, and elapsed time per work interval, followed by a list of subagent calls with their targets and outcomes. If no worker was available, state the reason. For a goal, keep this ledger through continuation turns and include it in the final goal report. The coordinator remains responsible for the final answer and verification.
